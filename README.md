# CanSight

CanSight 是基于 STM32F407 和 LVGL 的经典 CAN 总线查看与日志记录项目。设备使用触摸屏显示报文，将接收记录保存到 SD 卡，并支持在设备上筛选和逐帧查看历史日志。

项目保留“接收”和“SD 日志”两个页面，接收页提供状态、总帧数、报文表格、ID 筛选及翻页；历史页用于文件管理和手动逐帧查看，不提供手动发送报文和追踪页面。Windows 模拟器用于开发界面，与 STM32 固件共用界面和字体源码。

## 当前进度

项目已实现真实 CAN 报文显示、日志归档、历史列表、容量显示、删除、ID 筛选及逐帧查看，使用 64 位微秒时间戳记录采集时间。历史 ID 筛选及匹配计数已完成实机确认。逐帧边界、长时间时间戳回绕、10 MiB 自动切分及异常分支仍需独立验证；后续重点为稳定性和 1 Mbit/s 高负载接收能力。

| SD 日志 | 已实现批量写入、定期同步、启动及手动归档，新增 10 MiB 自动切分待验证 |

## 构建 STM32 固件

安装 CMake、Ninja 和 Arm GNU Toolchain，并确保 `cmake`、`ninja`、`arm-none-eabi-gcc`、`arm-none-eabi-g++` 可从终端调用。也可以使用 STM32 开发工具提供的相应工具链环境。

在仓库根目录执行：

```powershell
cmake --preset Debug
cmake --build --preset Debug --parallel 4
```

主要输出：

- `build/Debug/cansight.elf`：烧录和调试文件。
- `build/Debug/cansight.map`：链接映射，用于查看代码和数据占用。

使用 ST-Link 配合 STM32CubeProgrammer 或开发环境，将 ELF 文件烧录到开发板。

Release 构建：

```powershell
cmake --preset Release
cmake --build --preset Release --parallel 4
```

Release 文件位于 `build/Release/`。当前 Debug 使用 `-O0 -g3`，Release 使用 `-Os -g0`。

## 构建 Windows 模拟器

模拟器使用 Windows 本机编译器，不能使用 `arm-none-eabi` 工具链。下面以安装在 `C:/msys64` 的 MSYS2 UCRT64 GCC 为例，要求 CMake 和 Ninja 已加入 `PATH`。

在仓库根目录的 PowerShell 中执行首次配置：

```powershell
cmake -S simulator -B simulator/build -G Ninja `
  -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe `
  -DCMAKE_CXX_COMPILER=C:/msys64/ucrt64/bin/g++.exe
```

编译并启动：

```powershell
cmake --build simulator/build --target cansight_sim --parallel 4
.\simulator\build\cansight_sim.exe
```

如果 MSYS2 安装在其他位置，修改编译器路径。若运行时提示缺少 MSYS2 运行库，将对应的 `ucrt64/bin` 目录加入当前终端的 `PATH`。

修改界面后，关闭模拟器窗口，再执行编译和启动命令。更换编译器时应使用新的构建目录，避免沿用旧工具链缓存。

模拟器和开发板直接编译同一份 `GUI/App/ui.c` 与字体文件，因此界面改动会作用于两端。模拟器使用 Windows 显示驱动和系统内存分配；开发板使用 LCD、触摸适配及 `lv_conf.h` 中的内存配置。模拟器不包含 CAN 接收和 SD 日志硬件逻辑。

模拟器从工作目录下的 `simulator/logs/` 读取历史 CSV。可以将 SD 卡上的 `CANLOG_001.CSV` 等归档文件复制到该目录，也可以在启动时指定目录：

```powershell
.\simulator\build\cansight_sim.exe 'D:\CANLogs'
```

本机目录默认没有日志，不自动生成示例文件。复制的日志不纳入 Git。固件和模拟器共用目录分页、文件名校验及 CSV 解析逻辑，仅底层文件访问分别使用 FatFs 和 Windows C 运行库。

## 界面操作

- 点击“接收”或“SD 日志”切换页面。
- 点击 ID 输入框，使用十六进制键盘输入筛选值。
- 输入 `237` 或 `0x237` 均表示十六进制 ID `0x237`，按数值精确匹配。
- 输入框留空或点击“清除”时取消 ID 筛选。
- 同一 ID 的标准帧和扩展帧均可匹配，表格使用“类型”列区分。
- 接收页与历史页筛选均只影响显示，不改变接收统计、日志内容或归档规则。
- 接收页每页最多显示 8 条汇总记录，通过 `<`、`>` 翻页，按首次收到该报文组合的顺序排列。
- 类型列中的 `RTR` 表示远程帧；远程帧的数据列为空。只收到一帧时周期为 `--`，之后显示最近两帧的时间间隔，单位为毫秒，保留三位小数。
- 进入“SD 日志”页只刷新历史文件列表，不触发归档。`Refresh` 可手动重新扫描目录。
- 左侧按归档编号从新到旧显示文件，每页 4 项，通过 `<`、`>` 翻页。正在写入的 `CANLOG.CSV` 不在列表中。
- 点击文件名后高亮选中，右侧显示大小并分批扫描文件，`Indexing` 显示进度和已扫描帧数。扫描完成后显示总帧数、匹配数及最多五帧的浏览窗口。
- 历史页输入 ID 后点击 `Apply` 或键盘确认；编辑过程中不重新扫描，`Clear` 取消筛选。条件变化后从文件开头重建匹配索引，定位重置为第一条匹配帧。
- `Prev frame`、`Next frame` 每次移动一条匹配报文；高亮的首行是当前帧，其余行为后续匹配帧。`Match A/B` 表示当前匹配序号及匹配总数，`frame C/D` 表示首行在原文件中的报文序号及原文件总帧数。
- 索引未完成、正在定位、筛选尚未提交或已到边界时，相关导航按钮禁用。无匹配结果显示 `No matching frames`，不沿用其他文件或筛选条件的旧数据。
- 历史数据只通过手动操作前后帧或切换文件改变，不按时间自动推进。时间列继续显示报文的微秒时间戳换算结果。
- 退出历史页关闭读取资源，已经就绪的窗口保留；未完成的索引或手动定位会取消，需要重新选择文件。快速退出再进入时，主循环先释放旧资源，再受理新请求。
- `Archive log` 手动归档当前日志。手动或自动归档成功后，正在显示的文件列表自动刷新至首页。
- 文件读取状态与归档状态分别显示；读取失败不修改活动日志的写入状态。
- 模拟器归档区域显示本机预览说明，不执行日志归档。
- 日志页显示 `SD free: 剩余容量 / 总容量 MiB`；进入页面、点击 `Refresh`、归档或删除后更新。数值为查询时快照，不随每帧写入实时变化。
- 选中文件后点击 `Delete file`，确认弹窗显示固定文件名；点击 `Cancel` 不提交删除，点击 `Delete` 后由主循环关闭读取句柄并删除该历史文件。
- 删除成功后清除该文件的预览、重新扫描首页并更新容量；失败时显示数字和 FRESULT 名称。活动日志、目录及任意路径不能作为删除目标，不自动删除旧日志。
- 模拟器显示 `Disk free`，容量来自日志目录所在磁盘；删除操作会实际删除本机目录中选中的历史 CSV。
- 活动日志及最近归档信息显示在右侧文件状态区域。

`Indexing` 的百分比表示索引构建进度，扫描完成后才能进行前后帧定位。历史查看不向 CAN 总线发送报文，接收和日志记录仍由原有主循环任务处理。

## CAN 接收与日志记录

当前固件的数据流：

```text
CAN1 FIFO0 中断
    → 读取报文并记录 TIM2 时间戳
    → 放入软件接收队列
    → 主循环取出报文
    → CanLogger_AddFrame() 缓冲 / 写入 CSV
    → CanStats_AddFrame() 更新汇总

LVGL 100 ms 定时器 → 读取统计结果 → 刷新接收表格与总帧数

主循环另行调用 lv_timer_handler() 和 CanLogger_Process()
```

CAN 中断不调用 LVGL 或文件系统。界面由 `ui_init()` 创建，主循环持续调用 `lv_timer_handler()` 处理刷新和输入。

统计模块使用固定的 128 条汇总记录，以 ID、IDE、RTR 共同作为键。同一数值 ID 的标准/扩展帧、数据/远程帧分别统计。表满后，已有记录继续更新，新组合不入表并累计未入表帧数，界面显示 `ID table full` 提示。统计表容量不会限制日志写入，也不会因筛选而改变。

顶部总帧数为主循环交给统计模块的报文数量，包含未入表帧；它等于各条目计数之和加未入表帧数，不包含硬件 FIFO 或软件接收队列中丢失的报文。帧计数器为 32 位无符号数。报文时间和周期均使用 64 位微秒数，相邻报文间隔不再受原先约 71.6 分钟的 32 位范围限制。

软件接收队列分配 512 个位置，保留一个位置区分空与满，实际可用 511 帧；读写索引使用 16 位整数。主循环优先处理接收队列，每批最多 256 帧或约 2 ms，在完整报文处理后检查时间预算。追加报文可能触发同步写卡，因此 2 ms 不是单次调用的硬性超时。

LVGL 处理按约 5 ms 的运行间隔调度，页面数据仍约每 100 ms 刷新，表格内容相同时跳过单元格更新。历史文件处理间隔至少约 5 ms，软件队列占用超过 128 帧时延后执行。仅当接收队列为空时等待 1 ms，有积压时立即处理下一批。逐帧串口打印默认关闭；需要时可将 `CAN_RX_DEBUG_PRINT` 定义为 `1`，该模式会增加阻塞，不用于高负载验收。

### 运行状态与异常提示

状态栏和异常提示约每 100 ms 更新一次，不以是否收到新报文作为刷新条件。

| 显示 | 判定规则 |
| --- | --- |
| CAN1 未启动 | 控制器未处于监听状态，且未检测到启动失败或当前控制器错误 |
| CAN1 运行中 | HAL 状态为监听，且当前无错误警告、错误被动或 Bus-off 标志 |
| CAN1 错误 | 初始化或启动失败、HAL 错误状态，或当前存在上述控制器错误标志 |
| SD 未挂载 | 尚未成功挂载文件系统，包括启动时无卡或挂载失败 |
| SD 就绪 | 文件系统已挂载，但活动日志尚未就绪；当前主要为初始化中的过渡状态 |
| SD 记录中 | 活动日志已成功打开并完成初始同步，可以接受记录 |
| SD 错误 | 日志打开、格式化、写入或同步失败，日志功能已停止 |

“CAN1 运行中”表示控制器处于接收工作状态，不表示总线上一定有其他设备。停止报文发送不会改变该状态。错误警告或错误被动状态解除后可重新显示运行中；当前未实现 Bus-off 自动恢复及启动失败后的自动重试。

屏幕仅显示简短异常提示：`接收错误` 表示软件队列丢弃过报文或硬件 FIFO 发生过溢出，`CAN 错误` 表示累计 CAN 错误标志非零，`SD 日志错误` 表示日志操作返回过错误，`SD 记录错误` 表示日志模块拒收过报文。正常时异常栏不显示文字。顶部 CAN 和 SD 标签继续显示当前状态。接收页的匹配统计和输入框边框仅在内容或有效性变化时更新，避免周期刷新重复提交相同属性。

详细计数、HAL 错误位、FatFs 错误码和耗时保留在串口诊断或运行时快照中，不在日常页面持续显示。累计异常不随归档或切页清零；SD 状态来自文件系统操作结果，不提供独立的物理插卡检测，本阶段不支持热插拔后的自动重新挂载。

### 接收与存储性能诊断

接收调度与诊断已完成低负载实机检查：500 kbit/s、单条 8 字节标准帧、10 ms 周期下，发送与接收计数均为 6058，三个异常计数为 0。1 ms 周期下暴露 SDIO 发送 FIFO 欠载，改用 DMA 后，单条报文测试接收 138542 帧且异常计数为 0。双条报文测试出现软件队列丢帧及同步错误，不能据此认定达到 1 Mbit/s 不丢帧目标。

性能诊断通过串口和运行时快照提供：

- `CAN PERF`：硬件取帧数、处理数、软件丢帧数、硬件溢出事件数及队列峰值。
- `CAN PERF us`：接收处理间隔，以及批处理、界面、历史任务、写入、同步、归档的最长耗时，单位为微秒。
- `CAN UI` 与 `CAN TOUCH`：界面各阶段耗时、失效区域和触摸诊断。
- `CAN LOG`：日志接纳、写入、同步、缓冲和拒收计数。

统计在停止接收后通过串口输出；底层保留微秒值，失败操作也参与峰值统计。`CanStats_GetRuntime()` 发布的状态包含 `fifo_frames`、`queue_depth`、`queue_peak`、`queue_capacity`，以及 `max_service_gap_us`、`max_batch_us`、`max_ui_us`、`max_history_us`。调试时可在 `Core/Src/can_stats.c` 的 `runtime_state` 中查看完整快照。

`logger` 子结构区分本次初始化以来的各阶段计数，跨日志文件累计：

- `accepted_frames`：已完整复制至 RAM 缓冲的帧数。
- `rejected_frames`：有效输入中未被日志模块接纳的帧数，即串口 `CAN LOG` 中的 `rejected`。
- `written_frames`：完整缓冲经 `f_write` 成功写出的帧数。部分写入失败不计入完成帧数，即使卡上已有部分字节。
- `synced_frames`：最近一次成功 `f_sync` 时已经写出的累计帧数。
- `buffered_frames`：仍保存在 RAM 日志缓冲中的帧数，写入失败后保留。

计数使用 32 位无符号数并自然回绕。正常运行时，`accepted_frames = written_frames + buffered_frames`；停止发送、排空接收队列并完成下一次周期同步后，应有 `accepted_frames = written_frames = synced_frames`。这些软件计数不能替代 CSV 内容核对，异常卡的部分写入和断电持久性也不能仅凭计数判定。

SD 底层每次 DMA 块传输的软件等待上限设为 1000 ms，随后等待卡就绪的上限为 500 ms；`CTRL_SYNC` 同样确认卡就绪。卡就绪等待超时返回 `RES_NOTRDY`，传输失败返回 `RES_ERROR`，由 FatFs 向调用方报告。上述限制针对底层单次操作，不代表整个归档、容量扫描或删除只需这些时间；相关调用仍为同步执行，故障期间仍可能发生接收积压。

本次仅调整接收调度、缓冲容量、底层超时和诊断，正常 CAN 位速率仍为 500 kbit/s。后续按以下顺序进行实机确认：

1. 在现有位速率下确认正常接收、显示、归档和历史查看；正常记录时串口 `CAN LOG` 的 `rejected` 应保持 0。
2. 增加实际发送帧率并记录持续时间、队列峰值及最长调用耗时，同时观察 `Queue lost` 和 `FIFO overruns`。
3. 在接收期间执行归档、容量刷新、历史查看和删除，判断是否出现接收溢出；队列容量仍需根据最长阻塞实测调整。
4. 确认 SD 异常最终返回错误后，CAN 统计和界面能继续响应。停止记录后的新报文应增加串口 `CAN LOG` 的 `rejected`，本阶段不自动重新挂载。
5. 使用递增报文序号核对全部 CSV 文件的记录，再调整 CAN 位时序并验证 1 Mbit/s；不能以“总帧数增长”或单个溢出计数为零代替完整性检查。

#### 1 ms 周期发送时的写卡故障定位

实机在 500 kbit/s、单条 8 字节标准报文、1 ms 目标发送周期下出现 `SD LOG: error at write, FatFs result=1`。新增首故障诊断捕获 `HAL=0x00000010`、`TX_UNDERRUN=1`，失败请求为 3 个扇区，阶段耗时显示 0 ms；CRC、数据及命令超时标志均为 0。该结果确认 SDIO 发送 FIFO 欠载，耗时小于毫秒计时粒度，并非触发 1000 ms 的软件等待上限。原轮询实现依赖 CPU 持续向 FIFO 供数，接收中断打断搬运是重点排查路径，尚未独立测量每次中断耗时。

底层新增首故障快照，保存失败请求的操作、逻辑扇区、块数、阶段耗时、HAL SD 错误位和返回后的 SDIO 状态。首次日志停止时串口额外输出 `SD IO first fault` 及 `SD IO` 行，后续访问不会覆盖首因。`TX_UNDERRUN` 表示 SDIO 发送 FIFO 欠载，`RX_OVERRUN` 表示 SDIO 接收 FIFO 溢出，两者均与 CAN 接收 FIFO 不同；CRC、数据及命令超时分别输出。HAL 可能已清除硬件状态位，因此不能仅凭 `STA` 为零排除错误。

块读写现改为复用工程已有的 SDIO DMA 配置及中断，通过 BSP 完成回调通知驱动；回调仅置位，不调用 FatFs 或打印。使用普通 SRAM 中 16 字节对齐的 4096 字节中转缓冲，每次最多 8 个扇区，避免 FatFs 数据及元数据缓冲的对齐和 DMA 可访问性差异。传输成功后继续等待卡就绪，失败或超时先保留首故障现场，再中止 DMA 并锁存磁盘未就绪，防止后续历史访问隐式恢复或复用仍在传输的缓冲。该改动新增约 4 KiB 静态 SRAM 占用。

本次仍同步等待 DMA 和卡就绪，不在等待中重入文件系统，也不代表主循环阻塞或高负载丢帧问题全部解决。CAN 位速率及超时参数不变，没有增加自动重试。DMA 修改已获得单条 1 ms 周期发送的实机通过反馈。后续两条报文各 1 ms 的测试中，PCAN 总数为 127832，开发板处理 82988、软件队列丢弃 44844，队列峰值为 511/511；接收处理与存储组合负载仍未通过。归档文件中的记录属于已经处理的帧，不能再与接收总数相加。

#### 接收页静置时的软件队列溢出

后续在只停留接收页、两条标准数据帧各 1 ms 周期的测试中，PCAN 计数为 62022 与 61557，合计 123579；开发板处理 116383，软件队列丢弃 7196，两者合计与发送数一致。队列峰值为 511/511，硬件 FIFO 溢出及日志拒收为 0，SD 写入峰值为 24 ms、同步峰值为 5 ms。本档仍未通过，不能将先前丢帧仅归因于手动归档或历史页面。

停止来帧且软件队列排空约 1500 ms 后，主循环新增一次性串口摘要，再次来帧后重新等待静默；发送期间没有新增周期打印。`CAN PERF` 报告硬件取帧数、已处理帧数、软件丢弃、硬件溢出及队列峰值；`CAN PERF us` 报告接收批次开始间隔、单批处理、LVGL 处理、历史访问及写入、同步、归档的最长耗时，单位为微秒；`CAN LOG` 区分累计接纳、写入、同步、仍在缓冲及拒收帧数。摘要打印本身不计入下一批的服务间隔峰值。

原 `first CAN batch synced, frames=...` 提示现改为 `first periodic sync OK, file_frames=...`，表示每个活动文件首次周期同步成功时的累计接纳数；该数不要求固定等于发送帧率，初始化后同步计时与发送启用时刻不同，也不表示最终文件总数或丢帧数量。

此次仅增加静默诊断并澄清日志含义，尚未编译及上板确认，未据此认定积压根因。保持两条报文各 1 ms，先只停留接收页运行 10 至 15 秒，然后暂停两条发送并等待约 3 秒，保留全部 `CAN PERF` 与 `CAN LOG` 行，再根据实际耗时决定调度、显示或记录路径的修改。

#### LVGL 处理停顿的分项计时与首轮调整

一次双条报文各 1 ms 的短时测试中，PCAN 发送 18390 + 16980 = 35370 帧，开发板硬件取帧、处理、日志接纳、写入及同步计数均为 35370，软件队列丢弃、硬件溢出、日志拒收均为 0。但队列峰值达到 487/511，主循环接收批次开始间隔峰值约 294 ms，LVGL 处理峰值约 292 ms；写入及同步峰值分别约为 11 ms 和 4.5 ms。该次未丢帧不能代表已有足够余量，最长停顿需优先在 LVGL 路径内细分。

显示移植层现累计 LCD 刷新次数、传输耗时及像素数，输入移植层累计触摸回调耗时及 I2C 错误数。主循环在同一次最慢 LVGL 调用前后读取差值，静默摘要新增：

- `CAN UI peak`：该次调用总耗时 `total_us`、LCD 像素传输耗时 `lcd_us`、触摸处理耗时 `touch_us`、其余耗时 `other_us`、刷新块数 `flushes` 及像素数 `pixels`。`other_us` 包含软件绘制、布局、界面回调和框架调度，不能直接等同于纯绘制耗时。
- `CAN TOUCH`：累计回调次数、单次触摸处理最长耗时及 I2C 错误次数。该计数包含启动前的首次输入处理，`CAN UI peak` 则仅记录 CAN 启动后的调用。

同时实施两项调整：在 CAN 启动前完成初始化画面的整屏绘制；LCD 彩色矩形填充改为一次设置完整窗口，再连续写入所有像素，减少逐行重复设置窗口和命令的开销。LCD 传输仍为同步 CPU 写入，未增加显示 DMA，未更改 FSMC 时序、界面刷新周期、接收队列或日志缓冲容量。

该轮修改尚未编译及上板验证。重新烧录后暂停发送，待 `CAN1 Sight Start` 提示再启用两条报文各 1 ms，先验证画面、触摸和切页显示是否正常；接收页运行 10 至 15 秒后暂停两条发送，等约 3 秒，保留完整性能摘要。根据新的分项耗时及队列峰值决定后续优化，暂不提升总线位速率或发送负载。

#### LVGL 刷新事件与冻结统计对照

新增实验默认保持正常行为：`GUI/App/ui.h` 中 `UI_DIAG_FREEZE_STATS=0`。改为 `1` 并重新编译烧录后，统计定时器仅保留初始化显示，后续周期控件更新暂停；CAN 接收、底层统计、SD 日志、LVGL 调度和触摸继续工作。冻结模式下屏幕的 CAN/SD 状态、总数及历史状态停留在旧值是实验预期，应以串口为准；手动触摸事件仍可能修改控件，因此对照阶段均只停留接收页、不进行操作。启动串口打印 `CAN UI experiment: freeze_stats=...`，用于确认固件模式。

通过公开显示事件增加 `REFR_START/READY`、`RENDER_START/READY` 及 `INVALIDATE_AREA` 观测，不修改 LVGL 库源码或失效范围。初始整屏绘制完成后清零观测数据，仅保留 CAN 启动后的记录，停止发送且队列排空后统一输出。

`CAN UI stages us` 来自同一次最慢 LVGL 调用：

| 字段 | 含义 |
| --- | --- |
| `refresh` | 显示刷新事件的累计区间，包含布局、区域处理、渲染及同步 LCD 传输 |
| `render` | 渲染事件的累计区间，包含软件绘制与同步 LCD 传输 |
| `render_cpu` | 渲染区间减去其中的 LCD 传输，仍含框架开销和中断占用，不是排除中断后的 CPU 净执行时间 |
| `refresh_other` | `refresh - render`，包含布局、区域合并及刷新前后处理，不能单独等同于布局耗时 |
| `stats` | 周期统计控件回调耗时，不包含之后执行的软件绘制 |
| `handler_other` | LVGL 总耗时减去刷新区间、触摸回调和统计回调，包含其他定时器、输入事件处理及调度等 |

`render` 已包含 LCD 传输，`refresh` 又包含 `render`，三者不可直接相加。旧的 `CAN UI peak` 字段继续保留，便于与前一轮对比。

`CAN UI stats` 显示实验模式、统计回调次数及最长耗时、LVGL 调用次数及平均耗时。`CAN UI hist` 按小于 1 ms、1 至 5 ms、5 至 20 ms、20 至 50 ms、50 至 100 ms、不小于 100 ms 六个互斥区间累计调用次数，各区间右端不包含；用于区分偶发长停顿和持续慢调用，不直接输出精确 P95。

`CAN UI invalid` 是最慢调用期间收到的失效请求事件数及请求面积总和，允许重复或重叠，且请求可能在下次显示刷新才执行，不能作为同次真实重绘面积。`CAN UI area` 在整次运行中保留面积最大的八种不同请求矩形及坐标；`hits` 仅计条目保留期间的命中次数，不保证输出顺序或覆盖所有小矩形。事件也可能包含内部区域调整，应结合实际控件坐标分析，不能仅凭大矩形认定某个控件整块失效。实际传输像素仍看 `CAN UI peak` 的 `pixels`。

这轮仅增加观测与实验开关，未调整刷新周期、编译优化等级、缓冲容量或在 LCD 回调中执行 CAN/FatFs。尚未编译及上板验证。先用模式 0、500 kbit/s、两条报文各 1 ms，在接收页运行约 60 秒，暂停后等待约 3 秒并保存完整串口摘要；再设置模式 1，重新编译烧录，在相同条件下重复，比较调用耗时分布、刷新面积、队列峰值及完整性计数。下一次正常使用前恢复模式 0。

#### 频繁切页后的 FR_INVALID_OBJECT

实机在归档并多次切换接收、历史页面后报告 `error at sync, FatFs result=9`，该次日志没有底层首故障输出。源码检查发现，原 `SD_status()` 每次调用均发送卡状态查询，并将任何非传输就绪状态映射为 `STA_NOINIT`；项目所用 FatFs 的 `validate()` 会因此将原本已打开的文件对象判为无效。该逻辑确实混淆了初始化状态和瞬时传输状态，但本次现场尚不能独立排除句柄失效或内存损坏。

驱动现改为在初始化成功并确认卡就绪后清除 `STA_NOINIT`，普通 `SD_status()` 仅返回缓存状态；真实传输失败或等待超时仍锁存未就绪。块读写和 `CTRL_SYNC` 继续进行有界等待，不通过忽略传输错误维持记录，也不自动重新打开失效文件。同步报告 9 号错误时新增 `SD OBJ` 输出，记录文件系统指针是否匹配、文件及挂载编号、文件系统类型与磁盘状态，便于进一步区分原因。

此次状态语义修正尚未编译或上板验证。先保持同一发送负载，分别确认只停留接收页、反复切页、进入历史预览及手动归档时的状态。SD 同步错误和软件队列溢出是不同问题，错误消失也不能代替收发数量及 CSV 完整性核对。

`main.c` 的用户逻辑位于 CubeMX 的 USER CODE 区域。`FATFS/Target/sd_diskio.c` 的块读写及 `CTRL_SYNC` 修改包含生成区域，后续重新生成工程时须核对并保留这些改动。

### 日志归档规则

活动日志保存在 SD 卡根目录的 `CANLOG.CSV`，历史日志使用 `CANLOG_001.CSV` 等名称。

1. 启动时扫描现有历史文件编号，将旧的非空活动日志归档，再创建本次启动的活动日志。
2. 点击 `Archive log` 后，界面仅提交请求。主循环在写出缓冲、同步并关闭活动文件后执行重命名，成功后创建新活动日志继续记录。页面切换不归档。
3. 编号从现有最大编号递增，至少三位，超过 999 后自然扩展位数；最多支持九位编号。重命名前检查目标是否存在，不覆盖旧文件或同名目录。
4. 零字节文件及内容完全等于 CSV 表头的文件不生成历史文件。其他旧文件即使格式未知，也保留并归档，不按文件大小简单丢弃。
5. 当前日志没有接收记录时，归档请求返回 `No frames; archive skipped`，继续使用原活动文件。
6. 归档任一步失败即停止日志并显示错误，不截断已有数据。若归档成功但新活动文件创建失败，历史文件仍保留，归档状态显示失败以提示记录尚未恢复。
7. 活动文件达到约 10 MiB 时自动归档。大小计算包含 CSV 表头和 RAM 中待写出的记录，按完整报文边界切分，单个新生成文件不超过该上限；已有历史文件不重新切分。阈值由 `CAN_LOG_MAX_FILE_SIZE` 配置。

归档请求与接收出队处理均在主循环中顺序执行；实际切换文件之前处理的报文仍属于旧文件，之后处理的报文进入新文件。归档操作期间 CAN 中断仍接收并入队，但同步文件操作可能暂时阻塞主循环，不能据此保证高负载下零丢帧，应关注接收异常计数。

日志继续使用 4096 字节文本缓冲区，主循环约每秒写出剩余记录并调用 `f_sync()`。V0.4 支持手动删除历史日志，尚未实现 SD 热插拔恢复。

### 存储容量与历史文件删除（V0.4）

容量查询使用 `f_getfree()` 返回的空闲簇数和卷参数，按实际扇区大小换算，并在乘法前扩展为 64 位，避免大容量卡发生 32 位溢出。总容量表示文件系统的数据区容量，不是卡的标称容量；`1 MiB = 1,048,576` 字节。剩余空间包含整卷其他文件的占用影响，不包含尚未写入的 RAM 日志缓冲。

剩余空间小于 10 MiB 时显示黄色 `LOW SPACE` 提示。提示基于最近查询结果，不代表剩余可记录时长，也不保证还能写完一个完整日志。空间耗尽后的短写由日志模块报告为 `FR_DISK_ERR`，日志停止写入；删除文件不会自动恢复已停止的日志功能，需处理故障后复位。

删除请求锁定确认时的规范归档文件名，执行前关闭历史读取及目录句柄，并检查目标不是目录。固件使用 `f_unlink()`，模拟器使用 Windows 文件接口；模拟器还拒绝重解析点。活动 `CANLOG.CSV` 不符合归档名称校验，不能通过此接口删除。删除不重编号已有文件，日志模块继续使用当前分配的后续编号。

容量查询、删除、预览和活动日志写入均由同一主循环顺序执行，不在 LVGL 回调或 CAN 中断内访问文件系统。容量与删除错误独立显示，不覆盖活动日志模块的状态。容量查询和删除是同步操作：FatFs 首次查询可能需要遍历 FAT 表，删除需要释放文件簇链，较大卷或较大文件可能造成明显等待。CAN 中断在此期间仍可入队，但当前不能保证高负载下不发生队列溢出；相关性能优化保留至 V0.7。

本阶段不引入 RTC 或日期时间，继续保留 TIM2 报文时间戳用于周期计算及历史记录的时间分析。

常见 SD 错误如下，完整枚举以项目自带的 FatFs `ff.h` 为准：

| 错误码 | 名称 | 含义 |
| --- | --- | --- |
| 0 | FR_OK | 操作成功 |
| 1 | FR_DISK_ERR | 底层磁盘读写错误；短写也统一报告为此错误 |
| 3 | FR_NOT_READY | 存储设备未就绪 |
| 7 | FR_DENIED | 操作被拒绝、目录已满等；本模块编号耗尽也报告此错误 |
| 13 | FR_NO_FILESYSTEM | 未识别到有效 FAT 文件系统 |
| 16 | FR_LOCKED | 文件共享策略禁止当前操作 |

CSV 格式示例：

```csv
timestamp_us64,format,type,id,dlc,data_hex
123456,STD,DATA,0x237,8,12 27 65 74 83 92 87 33
123956,EXT,REMOTE,0x123,8,
```

| 字段 | 含义 |
| --- | --- |
| `timestamp_us64` | 本次启动的 64 位微秒时间，由 TIM2 与溢出计数共同产生，不是日期时间 |
| `format` | `STD` 为标准帧，`EXT` 为扩展帧 |
| `type` | `DATA` 为数据帧，`REMOTE` 为远程帧 |
| `id` | 十六进制 CAN ID |
| `dlc` | DLC，当前接收路径限制为 0～8 |
| `data_hex` | 以空格分隔的十六进制数据字节；远程帧为空 |

### 采集时间与旧日志兼容（V0.5）

硬件 TIM2 仍为 32 位、1 MHz；每次溢出由 TIM2 更新中断累加软件高位。TIM2 与 CAN RX0 的抢占优先级均为 0。读取时短暂屏蔽中断并保存、恢复原 PRIMASK；若已溢出但中断尚未处理，则在返回快照中补计一次，不修改软件高位，防止中断随后重复累加。启动前清除初始化产生的更新标志，并将计数器清零。

新日志使用 `timestamp_us64` 表头，首字段保存十进制 64 位微秒数，长时间无报文期间的回绕也由采集端累计。日志和界面通过专用整数格式化函数输出，不依赖精简 printf 的 `%llu` 支持。设备复位后重新计时，不添加 RTC、日期或设置时间页面。

读取器继续支持旧版 `timestamp_us` 表头，限制旧记录为 32 位数值；按全文件顺序在数值下降时累加 `2^32` 微秒，并在界面注明 `legacy 32-bit time: wraps inferred`。时间展开在筛选之前执行，索引保存对应上下文，向前定位不会重复累加。

旧格式无法区分一次回绕、多个回绕或旧固件跨复位追加造成的时间下降；已丢失的信息不能恢复，因此推断结果不保证还原真实长间隔。新 64 位格式不做这种推断，时间倒退直接报告 CSV 格式错误。升级不会改写已有历史文件；启动时对旧版仅含表头的活动文件校验后移除并重建，含记录的文件照常归档。

### 历史文件读取

`LogPlayer_Process()` 在主循环中位于日志处理之后。单轮最多扫描 4 个目录项或读取 1024 字节；不一次性加载整个目录或整份日志。分页扫描只保留当前页所需的 4 个候选条目，内存占用不随历史文件数增长。为保持编号排序，每次翻页会分批重新扫描目录，目录较大时显示 `Scanning...`。

选中文件或改变已提交的 ID 筛选后，分批扫描整个文件并统计原始帧数及匹配帧数，同时保存最多五个初始匹配帧。索引最初每 64 个匹配帧保存一个定位点，数组上限为 64 项；满后保留偶数项并将间隔加倍，使内存占用固定。每项保存字节偏移、物理行号、全局帧数、匹配数和上一帧时间。

上一帧、下一帧先恢复目标之前最近的索引点，再按同样的有界批次读取至目标，最多保留五帧，完成后关闭文件。不会为每条报文建立常驻索引，也不会因向前查看而丢失旧时间展开状态。首次完整扫描和筛选重建需要等待，较大文件及稀疏匹配可能等待较久；高负载下的读取吞吐优化保留至 V0.7。

文件名必须符合项目生成的 `CANLOG_001.CSV` 至九位编号格式，字母不区分大小写，不接受活动文件、目录或任意路径。预览使用只读模式；只有确认删除后才移除目标历史日志。固件 FatFs `_FS_LOCK` 已设为 4，并同步到 `.ioc`，用于容纳活动文件、历史读取和目录扫描。

CSV 首行必须匹配新旧两种日志表头之一，允许 UTF-8 BOM、LF 或 CRLF 行结束符。每条报文校验时间戳范围、STD/EXT、DATA/REMOTE、ID 范围、DLC 0～8 及实际数据长度；远程帧数据列必须为空。行缓冲固定为 128 字节，超长行或异常内容会停止读取并报告行号，保留此前有效窗口，但撤销导航能力，不将错误内容作为报文显示。

界面区分无历史文件、目录扫描失败、文件打开/读取失败、空日志、无匹配帧和 CSV 格式错误。导航仅在完整扫描完成后启用；扫描期间已显示的前几帧不代表文件已校验完成。历史文件按只读且内容不变处理；重新打开及读取时检测到大小变化，报告 `FR_INVALID_OBJECT`，需重新选择文件建立索引。模拟器中不要在浏览期间从其他程序修改同一日志；大小未改变的外部改写不在当前检测范围内。

如果底层资源关闭失败，读取模块暂停后续文件访问，避免覆盖未释放的文件对象；需要复位后重新初始化。本阶段未提供 SD 热插拔或故障后的自动恢复。

## 字体与内存

界面使用 `lv_font_cansight_14`，由 `NotoSansSC-Regular.ttf` 转换为 LVGL C 字体，字号 14 px、4 bpp，未启用压缩。字体仅包含 ASCII 和当前界面所需的中文、符号，不包含完整中文字库。

新增中文文案时，需要将新增字符加入字体转换范围并重新生成 `GUI/App/lv_font_cansight_14.c`。转换参数记录在该文件头部。字体源码已加入根目录和模拟器的两份 `CMakeLists.txt`；替换文件且保留名称时无需再次添加。

STM32 当前配置了 32 KB LVGL 内存池，另有 800 × 10 像素的 RGB565 显示缓冲区，占 16000 字节。链接报告中的 SRAM 占用包含预留的 LVGL 内存池，但不能反映池内运行时剩余空间。增加控件和业务缓冲区时，应同时关注链接占用、运行时分配和栈空间。

主栈预留为 4 KB，链接脚本和 CubeMX `.ioc` 已同步配置。归档函数与 FatFs 长文件名处理存在嵌套调用，编译器栈报告表明原先的 1 KB 预留不足；4 KB 是当前预留值，后续仍需结合中断嵌套和实机运行检查余量。

## 开发说明

- CubeMX 生成文件中的自定义代码应放在 `USER CODE` 区域，重新生成后检查差异。
- `Core/Src/can.c` 的 `HAL_CAN_Init()` 失败分支已改为返回，由主循环显示错误。该分支位于生成区域，CubeMX 重新生成后须核对，避免恢复为阻塞式 `Error_Handler()`。
- 新增共用界面源码时，分别更新固件和模拟器的 CMake 配置。
- 逐帧串口调试输出使用阻塞发送，默认关闭；开启后会影响高报文速率下的处理能力。
- `build/` 等构建目录与 `.vscode/` 本地配置不纳入版本管理。若本地关闭 cSpell，提交前应自行检查命名和拼写。
- STM32 HAL、CMSIS、FatFs、LVGL 和字体等第三方内容遵循各自附带的许可说明。
