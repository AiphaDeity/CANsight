## 第一课：一帧从CAN到CCM，再到主循环

### 1. 硬件FIFO不是软件队列

CAN1接收到一帧有效报文后，由外设保存到硬件FIFO。接收中断通知CPU来取，程序中的CCM数组是第二级缓冲。

```text
CAN硬件FIFO → 接收中断 → CCM软件队列 → 主循环 → 记录和统计
```

中断中的代码也是CPU执行，所以可以访问CCM；不是CAN外设或DMA直接写入CCM。

### 2. 一帧保存什么

`CanFrame`含64位接收时间、32位ID、IDE、RTR、DLC和8字节数据。字段共23字节，当前ABI对齐后结构体为24字节。标准帧和扩展帧都使用同一种结构。

队列2048个槽位占48 KiB CCM，采用空槽区分空和满，可用2047帧。数据数组在CCM；索引和计数在普通SRAM。

### 3. 中断做什么

入口是 `HAL_CAN_RxFifo0MsgPendingCallback()`：

1. 确认是CAN1，检查FIFO内是否还有帧。
2. 读取报文头和数据，取得微秒时间戳。
3. 根据IDE选择标准或扩展ID；DLC限制到8，远程帧不复制无效数据。
4. 调用 `CAN_RxQueue_PushFromISR()` 入队。

中断不执行文件写入、界面绘制和串口长输出。这些操作耗时更长，留给主循环。

### 4. 环形队列如何入队

关键变量：

```c
head      // 中断下一次准备写入的位置
tail      // 主循环下一次准备取出的位置
nextHead = (head + 1U) & CAN_RX_QUEUE_MASK;
```

2048是2的整数次幂，掩码为2047，即低11位全为1。它让下标从2047再加1时回到0。

| 条件 | 含义 |
| --- | --- |
| `head == tail` | 空 |
| `nextHead == tail` | 满，本帧不写入，增加软件丢帧计数 |
| 其他情况 | 当前head槽可写 |

空队列时 `head=0, tail=0`；写入一帧后 `head=1, tail=0`；主循环取走后 `head=1, tail=1`，再次为空。

入队顺序是：

```c
canRxQueue[head] = *frame;
__DMB();
canRxQueueHead = nextHead;
```

先把整帧复制好，再发布新的head。`__DMB()`约束内存访问顺序，防止消费者在槽内容可见之前看到head已经前进。

### 5. 主循环如何取出

`CAN_RxQueue_Pop()`先比较head和tail。非空时，将tail对应的完整帧复制到主循环自己的局部变量，再推进tail，释放这个槽位。

不能先释放槽位再复制：如果中断在这之间运行，生产者可能复用槽位并覆盖尚未读完的数据。

当前只有一个生产者和一个消费者：中断更新head，主循环更新tail。ISR执行时主循环不会同时执行；主循环会被ISR打断，因此仍要遵守发布和释放顺序。

`volatile`用于让共享索引按实际访问读写，不等于互斥锁，也不能让结构体复制或64位访问自动成为原子操作。顺序屏障、对齐索引和单生产者/单消费者约束共同支撑当前实现。

### 6. 出队后如何处理

主循环依次执行：

```c
CanLogger_AddFrame(&frame);
CanStats_AddFrame(&frame);
```

前者按记录状态接纳报文，后者更新统计。记录失败不阻止统计继续；回放期间记录主动暂停，统计仍更新。页面筛选只影响显示，不截断这条后台处理链。

软件队列中的帧被处理后就释放，不能当作长期保存空间。若记录暂停，这段时间的帧不会在恢复后补存。

### 7. 怎样判断你已经理解

先不看答案，自己讲一遍：

1. 为什么2048槽只能放2047帧？
2. 为什么先复制帧，再更新head？
3. 主循环复制到一半被中断打断，生产者为什么不会覆盖这个未释放的槽？
4. `volatile`与`__DMB()`分别做什么，为什么不可以互相代替？
5. 队列扩大以后，什么问题可以缓解，什么问题仍会发生？
6. 回放时接收到的帧去了哪里，为什么不增加日志拒收计数？

能用head/tail的具体数字说明一次入队、一次出队和一次满队列，比背函数名更重要。

## 第二课：主循环调度

围绕 `main()` 的while循环阅读，依次找串口服务、回放服务、接收批次、日志周期处理、UI和历史浏览。

- 每批最多256帧，并在帧之间检查2 ms预算，保证其他功能有机会运行。
- 单帧追加日志可能包含同步写卡；因此2 ms不是能强行中断所有调用的硬上限。
- UI积压阈值为256/64，使用两个阈值防止在边界反复开关。
- 5 ms的LVGL调度和500 ms的页面数据更新是两件事，也不等于报文接收周期。
- 2047帧在实际8000帧/s且完全不消费时约256 ms就会用完。队列吸收短暂停顿，不能弥补长期吞吐不足。

## 第三课：时间戳与统计

TIM2低32位以1 MHz计数，约71.6分钟回绕一次；溢出计数作为高32位。读取时保存PRIMASK、临时关中断、读取高低位并补偿待处理溢出，最后恢复原来的中断状态。不要简单把恢复写成无条件开中断。

统计按ID、IDE、RTR三者区分，最多128种组合。计数是累计帧数，周期是最近两帧接收时间差；统计表满不等于日志停止。界面只显示部分条目，不能将当前可见行数当成全部已接收数量。

## 第四课：日志、DMA和归档

- CSV先进入4 KiB日志缓冲，满时写出，约每秒周期同步。
- `accepted`表示接纳到RAM，`written`表示文件写入成功，`synced`表示最近同步时的写入数量，三个阶段不同。
- 工程自有DMA磁盘适配调用官方BSP/HAL，不是自行实现DMA控制器。4 KiB中转缓冲留普通SRAM，照顾地址对齐和DMA访问限制。
- DMA减少CPU搬运工作，但当前FatFs调用仍同步等待DMA完成和卡就绪，主循环在这期间不能继续正常消费队列。
- 归档包括刷出、同步、关闭、重命名和新建活动文件，会造成额外停顿。

## 第五课：历史浏览与回放

历史页用请求和状态推进目录、索引、浏览；稀疏定位点存在RAM，不是加载整个文件。`Frame`是原文件位置，`Match`是筛选后的位置。

回放保留完整文件顺序，以第一帧时间为基准调度。预读最多64帧，一次只有一个在途邮箱，确认TXOK才增加成功数。暂停会调整时间基准，Stop是请求，进入STOPPING之后还要确认硬件状态，不能立即假设结束。

思考：一帧已上总线但尚未轮询时按Stop，如何避免漏记？取消请求返回成功，为什么还要检查邮箱？总线忙引起的延迟和文件读取延迟如何区分？

## 代码讲解顺序

1. **需求**：持续接收和记录，支持查看、筛选及回放。
2. **架构**：中断取帧入队，主循环处理，显示刷新降频，SD批量记录。
3. **问题**：高负载下UI/存储长调用导致软件队列满，硬件FIFO和软件丢帧分开计数。
4. **取舍**：减少无用重绘、复用键盘、设置积压保护、使用CCM缓冲；保持裸机，暂不加RTOS和LCD DMA。
5. **证据**：描述具体实测帧数、操作和计数一致性，说明目标速率与实际总线测量的区别。
6. **限制**：回放期间不记录新帧，Bus-off恢复和异常存储场景未完善，不能承诺任意故障下不丢帧。

阅读时区分库提供的能力和项目自身实现，结合源码理解配置、设计取舍、排查过程及验证结果。不清楚的细节回到源码确认，尚未验证的恢复能力保留为已知限制。
